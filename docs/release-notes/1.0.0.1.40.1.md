# Invio v1.0.0.1.40.1 — Refrens Email / Settings Brand / Nuitka Build Correction Candidate

Status: **LOCAL ERROR-FIX CANDIDATE — DO NOT TAG OR RELEASE YET**.

Official owner-frozen parent baseline: **v1.0.0.1.40**.

## Primary evidence and root causes

### Refrens email

Owner live v1.40 evidence confirms the Refrens account is verified, Task execution completes 7/7, and seven real invoices are created in Refrens. That evidence does not show actual recipient email triggering. v1.40 considered the create-invoice request sufficient provider-send evidence even though Refrens also exposes an explicit invoice email endpoint.

v1.40.1 keeps the successful invoice-create payload and makes the send boundary explicit:

1. create invoice;
2. require and persist returned `_id`;
3. POST the recipient to `/businesses/:urlKey/invoices/:invoiceID/email`;
4. mark provider send acceptance only after the email endpoint succeeds.

A definitive email-endpoint failure leaves the invoice reference durable. `Retry Failed` reuses that invoice ID and retries the email trigger rather than creating another invoice. Ambiguous mutations remain fail-closed under the existing P10 policy.

### Settings UI

The v1.40 Settings page contained Settings-only smaller font and spacing overrides despite the uploaded official Vib Tools frozen validation source already defining shared page/card/form tokens. v1.40.1 removes only those Settings-specific deviations and uses the existing shared page padding, content gaps, card padding, typography and input contract. No other page is redesigned.

### GitHub / Nuitka

GitHub Actions run `31411715607`, job `93531112926`, passed dependency install, full regression audit, wheel work and native keyring/resource smoke, then failed at **Build Nuitka OneDir**. The v1.40 workflow passed `.github/nuitka-keyring.nuitka-package.config.yml`, but pinned Nuitka 4.1.3 already contains a standard `keyring` package configuration. Nuitka therefore stopped on duplicate module configuration.

v1.40.1 stops passing the custom user package-config file. The existing explicit `keyring` dependency inclusion and compiled protected-credential smoke remain unchanged.

## Agiled

Agiled remains fail-closed. Current published Agiled materials do not provide one internally consistent contract that can be implemented without changing the frozen provider credential model: the current product page describes Bearer-token authentication, while the published OpenAPI document specifies an `api_token` query parameter plus a required `Brand` account-URL header for invoice operations. Invio's packaged Agiled manifest currently contains only `api_key`. Enabling Agiled here would therefore require a separately approved credential/runtime contract rather than an error-only correction.
