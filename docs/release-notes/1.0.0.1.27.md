# Invio v1.0.0.1.27

## P10 - Persistent Delivery Ledger, Idempotency and Recovery

P10 makes supported Stripe Task delivery state auditable and restart-safe while preserving the existing Task, provider, scheduling and one-QThread-per-Task architecture.

- SQLite advances from schema v4 to **schema v5** through the existing transactional, WAL-aware, pre-migration-backup path.
- Exactly three durable delivery-ledger tables record execution runs, per-run recipients and provider operations.
- Every First Run, Resume Remaining and Retry Failed invocation receives a unique durable `run_id` distinct from `Task.id`; `Task.id` remains the canonical logical Stripe idempotency identity.
- Each Task provider operation records durable `Started` evidence before transport, including recipient/account binding, stage, P08 attempt number and the existing deterministic Stripe idempotency key where applicable.
- Successful operations persist provider customer/invoice references when available. Failures persist sanitized class/code/message evidence.
- Interrupted side-effecting operations become `Uncertain` after restart rather than being guessed as failed or successful.
- Durable recipient outcomes become authoritative for restart recovery, aggregate Task reconciliation, Resume Remaining and Retry Failed.
- P09 exact attempted-account binding survives restart; recipients with prior provider execution cannot switch accounts.
- Historical delivery-ledger rows remain after Close Task; no new UI page, report export, retention control or P11+ provider behavior is introduced.
- Pre-P10 non-pristine Tasks receive no fabricated historical delivery records and remain fail-closed for continuation that cannot be proven safely.

Production progress: **10/14**. Next phase: **P11 - Refrens End-to-End Task Enablement**, subject to separate approval.
