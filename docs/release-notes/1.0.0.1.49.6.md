# Invio v1.0.0.1.49.6 — Provider Fatal-Limit Circuit Breaker

## Parent baseline

- Parent application: `Invio v1.0.0.1.49.5`
- Parent Git commit: `8942477949cf61e169156032e3574377bf6d6fc7`
- Scope: Phase 2 — Provider Fatal Error / Account Limit Circuit Breaker & Task UX
- Phase-1 live RDP acceptance: intentionally deferred by owner until the final combined release.

## Confirmed defects corrected

1. The generic external-provider recipient loop previously reconciled an errored recipient and then unconditionally continued to the next recipient. A provider-wide/account-wide terminal condition therefore caused repeated customer/invoice/send work instead of stopping the batch.
2. Odoo mail evidence could report the proven daily email limit (`You have reached your daily limit of N emails.`), but the adapter exposed only a normal non-retryable `provider-mail` error and gave the host no machine-readable stop signal.
3. Odoo post-send evidence status `UNVERIFIED` was logged but the adapter still returned `ExternalRecipientResult`, allowing an ambiguous non-idempotent send outcome to be recorded as confirmed success.
4. External progress text used raw loop-attempt counts while the visible/durable counters used safe delivery results, producing messages such as `Processed 43/47` while most recipients remained Uncertain/Pending.
5. Worker terminal reconciliation could overwrite the actionable provider stop reason with a generic Stopped message.

## Implementation

- `ProviderRuntimeError` gains optional backward-compatible `halt_batch`, `halt_code`, and `user_message` metadata. Defaults are non-halting, so existing external adapters retain their behavior.
- The generic external batch loop always reconciles the current recipient first. If the caught error declares `halt_batch=True`, it emits one durable summary progress event and aborts before another recipient begins.
- A current recipient with a successful non-idempotent mutation remains `Uncertain`; untouched recipients remain `Pending`.
- Ordinary recipient-specific external errors continue to the next recipient exactly as before.
- External progress now reports durable `resolved / success / failed / uncertain / pending` values instead of raw loop-attempt counts.
- Existing MainWindow terminal reconciliation preserves a provider-generated `Stopped:` message on the current Task card.

## Odoo provider v1.0.1

- The proven daily-email-limit evidence is classified as `provider-quota`, non-retryable, `halt_batch=True`, `halt_code=daily-email-limit`.
- `UNVERIFIED` post-send mail evidence is classified as non-retryable terminal evidence uncertainty with `halt_code=mail-evidence-unverified`.
- `SENT` and `QUEUED` remain success-eligible.
- Recipient-specific `FAILED` mail evidence remains non-halting unless it matches the proven daily-limit condition.
- Odoo JSON-RPC workflow, account credentials, invoice/customer/send operations and `scheduling_policy = None` are unchanged.

## Continuation safety

No new Task state is introduced. A batch-halt exception reaches the existing worker boundary; durable Pending/Uncertain recipients cause the existing terminal reconciliation to produce `Stopped`. `Resume Remaining` for generic external providers continues to exclude Uncertain recipients automatically, so already-attempted non-idempotent outcomes are not replayed.

No automatic Odoo cross-account quota failover is introduced in Phase 2.
