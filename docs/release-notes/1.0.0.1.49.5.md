# Invio v1.0.0.1.49.5 — Windows/RDP Native TLS Trust Correction

## Scope

Phase 1 only: shared ProviderRuntime HTTPS trust compatibility on Windows/RDP. No provider business logic, Task, WorkerManager, storage, OAuth contract, IVX behavior, Settings UI, or Phase 2-4 feature work is changed.

## Verified root cause

On the affected Windows Server 2025 RDP host, `https://applemobileshopnow.odoo.com` succeeds through Windows native certificate validation, .NET HTTPS, and curl/Schannel, while the frozen Invio v1.49.4 packaged Python/OpenSSL transport reports `CERTIFICATE_VERIFY_FAILED: unable to get local issuer certificate`. The Windows chain engine builds the valid `*.odoo.com -> Let's Encrypt YR1 -> Root YR -> ISRG Root X1` chain. This proves a packaged Python/OpenSSL versus Windows native trust-chain divergence rather than an Odoo credential, DNS, proxy, hostname, or general Windows trust failure.

## Correction

- Windows ProviderRuntime HTTPS requests now use `truststore.SSLContext(ssl.PROTOCOL_TLS_CLIENT)`, which delegates certificate verification to the native Windows CryptoAPI trust store.
- Certificate verification remains `CERT_REQUIRED` and hostname verification remains enabled.
- HTTP/1.1 ALPN is explicitly configured for the custom context.
- Non-Windows transport keeps the existing stdlib `urlopen()` path unchanged.
- If the native trust backend is unavailable or cannot initialize, Invio fails closed with a permanent TLS error; it never falls back to an unverified connection.
- The same shared transport is used by built-in/external provider requests and OAuth discovery requests, so no Odoo-specific TLS workaround is introduced.

## Distribution contract

`truststore>=0.10.4,<0.11` is a required runtime dependency. Windows wheel smoke verifies the native context, Nuitka explicitly includes `truststore`, the portable audit requires it, and both compiled OneDir and MSI-installed executables run a fail-closed TLS-backend smoke.

## Security invariants

This release does not introduce `verify=False`, `ssl.CERT_NONE`, disabled hostname checks, hard-coded provider certificates, HTTP downgrade, or certificate-error suppression. Existing `SSLCertVerificationError -> category=tls, retryable=False` behavior remains intact.
